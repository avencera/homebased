# T3 Code

Read this when the `t3-code` MCP tools are present in your session, or before starting a T3 thread on another machine. Without T3, nothing else here applies.

## Delivery

When a T3 Code thread owns a Claude Code session or a Codex thread, the daemon starts the callback turn through T3 instead of the messaging socket or `codex queue`, so the thread shows it. [messages.md](messages.md) has the exact rules, including retries and unowned sessions.

## Terms

- **root thread**: a T3 thread the user started.
- **subagent**: short agent work whose result the caller uses in the same session. An **in-session subagent** is Claude Code's `Agent` tool and finishes within the turn. A **T3 subagent** is a `delegate_task` child: short work, typically under an hour, that never waits on long work, because T3 reports it done to its parent as soon as a turn ends with no wait running.
- **child thread**: a top-level T3 thread that another thread, its **parent thread**, launched with `homebased t3 launch --child` to own a phase, an experiment, or a long run. It can launch child threads of its own (**grandchildren**). It reports to its parent with `homebased thread report`, and homebased then settles it. A later message that reopens it can lead to a follow-up report.
- **worker**: a headless agent that homebased runs as a task (`HOMEBASED_TASK_ID` is set). It is not a T3 thread. It parks with `waiting` and continues as a new run ([worker.md](worker.md)).
- **task**: a homebased task, from `task run` or `task submit`. **job**: a GPU queue job, from `resource job submit`. **long work**: a task, job, or chain expected to run or queue for over an hour.
- **sleep**: `homebased wait --long`. The thread hands its long work to the daemon, goes idle, and wakes only on a **final event** (a task's terminal event, `JOB_SUCCEEDED`, `JOB_FAILED`, or `JOB_CANCELLED`) or an **alert**. Every other event is an **interim event**: an alert needs action before the work can end (`JOB_ATTENTION`, `JOB_BLOCKED`, `TASK_CHECK_DUE`, `TASK_MEMORY_REVIEW`, `JOB_CHECK_DUE`, the first `JOB_GPU_IDLE` of an idle episode), and a **progress event** needs none (`TASK_REPORTED`, `TASK_WAITING`, `JOB_PREEMPTED`, `JOB_GPU_IDLE` reminders).

## Choosing the runner

Pick by how long the work runs and who integrates it:

- Work that finishes within this turn: an in-session subagent.
- Short agent work whose result you integrate, such as a lookup, a review, or a quick edit and check: a T3 subagent with `delegate_task`, so T3 shows it under the thread. It does no long work.
- A phase, an experiment, or long work: a child thread, launched with `homebased t3 launch --child` ([child-thread recipe](#child-thread-recipe)). It submits its own tasks and jobs and sleeps on them. Never launch one with `t3_thread_launch`, which records no link, so the parent could not list it, wait on it, or tell a finished child from a stalled one.
- Unattended headless agent work that reports back as events: a worker, as an `agent` task.

Homebased stays the choice for `task` and `container` workloads, Fleet, the resource queue, and `after`. A thread waits on its own tasks and jobs; it never waits on another thread's.

Do not use a background Bash command for long work:

- Anything long-lived that you start and do not wait on, such as a dev server, a binding proxy, an emulator, or a phone test runner: `homebased service start --name <label> [--port <n> | --ready-line <regex>] -- <command...>`. It returns once the service is ready, runs outside your shell, and is stopped when this T3 thread is archived or settled, so nothing is left running after the thread is done. Stop it yourself with `homebased service stop <id>` once the work no longer needs it. See [services.md](services.md).
- A long test run, build, or other command whose result you need: `homebased task run --name <goal> -- <command...>`, then wait on it as below.

The only background Bash command a T3 thread should start is `homebased wait`.

## Waiting in a Claude thread

By default each event starts a new T3 turn, and the thread shows as idle between events. For work expected to take an hour or less, start `homebased wait --next` as a background Bash command right after you submit, whether with `task run`, `task submit`, or `resource job submit`, then pass its background task id to the `t3-code` tool `t3_background_wait`, so T3 shows the thread as Waiting and the events arrive inside the live session. A background command alone leaves the thread listed as running:

```text
Bash(
  command: "homebased wait --next <id> [<id> ...]",
  description: "<what the work does>, e.g. cargo build and the GPU training run",
  run_in_background: true,
  timeout: 7200000
)
t3_background_wait(taskIds: ["<background task id>"])
```

Then tell the user the task and job ids and end the turn. When a T3 thread owns the submitting Claude session, `task run`, `task submit`, and `resource job submit` print these steps for the new task or job as a `T3:` line on stderr; in a T3 subagent the line gives the subagent's wait instead.

Use a background command, not `Monitor`. A Monitor is killed after at most 30 minutes, and each expiry wakes the thread with nothing to report, which for a GPU job that sits in the queue for hours means a wasted turn every half hour. A background command wakes the thread only when it exits. Always give it `timeout: 7200000`, Claude Code's maximum, and let the wait pick its own limit: with no event, it exits after 55 minutes. A T3 Claude session caches its prompt for an hour, so a wake-up inside that hour reads a warm cache, while one after it rewrites the whole context, about $0.90 at 150K tokens of Opus. `--next` makes it exit once the next events are printed, so each event still wakes the thread promptly. For long work, sleep instead, as the next section says.

- A worker (`HOMEBASED_TASK_ID` is set) never starts a wait and keeps using `waiting`.
- A T3 subagent has no `HOMEBASED_TASK_ID`. It waits with `homebased wait --next --final-only` plus `t3_background_wait` on the short tasks and jobs it submitted, and starts that wait again before it ends any turn that is not its final one ([T3 subagent recipe](#t3-subagent-recipe)).
- Pass task ids and GPU queue job ids the same way, 1 to 16 in total, in one wait; the daemon works out which is which. Each must have been submitted from this session on this machine; a job may run on any machine. Any other id fails at once: `wait_unavailable`, whose message says why, or `wait_target_not_found` for an id that is not a task, job, or watch of this machine. Do not pass the task id of a queue run; it is refused. Watch ids from `homebased thread watch` ([threads.md](threads.md)) count too; a watch of another caller fails with `wait_unavailable`.
- Each stdout line is one `HOMEBASED_EVENT {...}`, handled as in [events.md](events.md). With `--next`, the command exits 0 about a second after it prints the first event, together with any that arrived in that second; read its output when it exits. Without `--next`, it exits 0 once every target has its final outcome. A task follows `TASK_WAITING` to its continuation. A job ends on `JOB_SUCCEEDED`, `JOB_FAILED`, or `JOB_CANCELLED`; `JOB_PREEMPTED`, `JOB_ATTENTION`, `JOB_BLOCKED`, and `JOB_CHECK_DUE` are printed and the wait goes on. A `JOB_ATTENTION` that comes after the job's final event arrives through normal delivery. A watch prints `THREAD_CONTEXT_OVER` or `THREAD_STALLED` and goes on, and ends on `THREAD_WATCH_ENDED`, or on a firing event with `watch_ended: true` from a `--once` watch. The command rides out a daemon restart.
- Add `--final-only` to `--next` to exit only on a final event or any watch event. Interim events such as `TASK_REPORTED`, `TASK_CHECK_DUE`, `TASK_WAITING`, `JOB_PREEMPTED`, and `JOB_GPU_IDLE` are still printed and confirmed as they arrive, so read the whole output when it exits. Use it when an interim event needs no action from you, as in a T3 subagent.
- Do not pipe it through `tail` or `head`: they hold every line until the command exits.
- After handling its output, start it again with the ids whose final event you have not seen. When it reached its limit with no event, it prints that command on stderr, with the ids still pending; run that one. Either way, register the new background task with `t3_background_wait`. Stop once every id has its final event. Events that arrive while no wait runs go through normal delivery, so one can arrive twice; deduplicate task events by `(task, seq)`, job events by `(job, seq)`, and watch events by `(watch, seq)`.

### Sleeping on long work

For long work, run `homebased wait --long` as an ordinary Bash command, not in the background and with no `t3_background_wait`, then tell the user the ids and end the turn:

```text
homebased task run --name "training run" -- ./train.sh     # prints <task id>
homebased wait --long <task id> [<job id> ...]              # exits at once
```

- It checks the ids as `homebased wait` does and prints one line per target on stderr, such as `homebased wait: task <id>: held`, then exits 0. `already_ended` means the final event already settled and nothing is held; handle that event if you have not. `followed_to <continuation>` means the task parked and the hold is on the run that continues it. A watch id reads `watched`, since every watch event wakes the thread anyway.
- The daemon then wakes the thread with each target's final event, whose line lists what the hold kept under `held_events` (see [events.md](events.md#held-events)), or with an alert. After an alert the hold stays: handle it and end the turn again, without starting another wait.
- Progress events never wake the thread. `TASK_WAITING` moves the hold to the continuation run, so a worker's chain stays held to its end. The tasks and jobs the worker parked on are held with it, provided their events come to this thread, as a worker's own submissions do: their progress events and their final events join the chain's `held_events`, since the continuation reports on them, and only their alerts wake the thread.
- The hold is saved by the daemon and survives a daemon restart. A `homebased wait` connected to the same target still takes its events first, so run one or the other. A hold on a job counts toward the idle compaction size and `thread report` only as long as a job counts as owing events, at most seven days, in case its queue machine never sends a final event.
- A sleeping thread certainly resumes after its prompt cache lapsed, so the daemon compacts it while idle from 60K tokens instead of 175K, and the event that wakes it waits behind that compaction (see [threads.md](threads.md#idle-compaction)). Do not compact it yourself first.
- A T3 subagent cannot sleep, because T3 reports it done to its parent as soon as its turn ends. `--long` waits up to 115 minutes there instead and says on stderr that long work belongs in a child thread. A worker gets a `usage` error and parks with `homebased task report --outcome waiting --on <id>`.

### T3 subagent recipe

A T3 subagent, started with `delegate_task`, runs short work only. When it submits a short task or job, such as a build or a test run:

```text
homebased task run --name "release build" -- cargo build --release      # prints <task id>
Bash(
  command: "homebased wait --next --final-only <task id>",
  description: "release build",
  run_in_background: true,
  timeout: 7200000
)
t3_background_wait(taskIds: ["<background task id>"])
```

End the turn. When the wait exits, handle its events; if any id has no final event yet, start the wait again with those ids and register it before ending the turn. A subagent that ends a turn with no wait running looks finished to T3, which wakes its parent for nothing. Give the final answer only once every id is done. Work that would run or queue for over an hour does not belong in a T3 subagent: say so in the final answer, so the caller moves it to a child thread.

### Worker recipe

A worker that needs a long command submits it as its own task or GPU queue job, reports `waiting` on the task and job ids with notes for the next run, and exits ([worker.md](worker.md#long-commands-submit-and-wait)). Homebased starts the continuation once every target ended. A thread that sleeps on the worker hears nothing of this until the chain's final event.

### Orchestrator recipe

A T3 root that coordinates work launches a child thread for each phase, experiment, or long run, and uses T3 subagents only for short work:

1. Launch child threads with `homebased t3 launch --child` ([child-thread recipe](#child-thread-recipe)), and start T3 subagents with `delegate_task`.
2. Watch stalls with `homebased --json thread watch --children --stalled-after 20m`, so a child thread or T3 subagent that ends its turn without reporting and sits idle wakes you with `THREAD_STALLED`. It covers the children live when you run it; run it again after launching more.
3. Watch context one thread at a time: your own thread with `homebased --json thread watch --context-above <limit> --action compact`, and each Claude T3 subagent with `homebased --json thread watch <subagent-thread-id> --context-above <limit> --action compact`, using the thread id `delegate_task` returned. Never use `--children` for context watches: it has no model filter, so it also catches Codex threads. A child thread owns its own context; daemon idle compaction covers it while it sleeps. The orchestrate skill sets the default limits.
4. After your own compaction, `homebased --json thread context --children` lists every child thread and T3 subagent, finished ones included, with title, link, state, and context; a child thread has a `child_thread` record that says whether it reported. See [threads.md](threads.md).
5. End the turn. Each child thread's report arrives as one `HOMEBASED_MESSAGE`; your thread shows `waiting` until every child has reported.

## Waiting in a Codex thread

Codex cannot run a background command that wakes it. Submit and end the turn; each event starts a new turn, and T3 shows the thread as idle between events.

## Launching a thread on another machine

The `t3-code` MCP tools reach only the T3 on this machine. To start a thread in the T3 on another Fleet machine, use `homebased t3 launch`, which works from any shell, inside T3 or not:

```bash
homebased --json t3 projects --machine code
homebased --json t3 project add ~/code/app --machine code   # only when it is missing
homebased --json t3 launch --machine code --project ~/code/app \
  --message-file brief.md --worktree main --branch fix/upload
```

- Use it when the user asks for a new thread or independent work on that machine, the way `t3_thread_launch` serves this one, or with `--child` for a child thread here or there. Use a homebased task instead for background work that should report back to this thread as events.
- `--project` is a T3 project on that machine: its id, its workspace root there (absolute or `~/`, which resolves under that machine's home even when your shell expands it), its exact title, or the repository it checks out, as `owner/repo` or a remote URL. Paths differ between machines, so prefer the repository: it matches the project whose `origin` remote names the same repository, whatever its form (SSH or HTTPS, `.git` or not, any case). `owner/repo` matches on any host; a URL or `host/owner/repo` matches that host only. A project missing there fails with `t3_project_not_found`, lists what exists, and has `input.repository: true` when `--project` named a repository. A machine whose homebased predates repository matching answers `t3_incompatible` for one.
- `--clone-if-missing` clones the repository `--project` names into `~/code/<repo>` on that machine, or `--clone-into <dir>`, adds it as a project, and launches there, when no project checks it out. `owner/repo` clones from GitHub, over SSH when another project there already reaches GitHub over SSH, else HTTPS; a URL clones as given. A directory already there that is a clone of the repository is added as it is, so a retry clones nothing twice; any other directory there fails with `t3_launch_refused`, and so does a clone that fails, with git's reason. A machine whose homebased predates clones answers `t3_incompatible`.
- `t3 project add <path> [--title <title>]` adds an existing directory on that machine as a project; the JSON result has `project.project.id` and `project.existed`, which is `true` when the directory already was a project. It does not clone: a directory missing there fails with `t3_project_refused`, so launch with `--clone-if-missing` instead.
- `t3 project add` also takes an icon, applied whether or not the project already existed: `--lucide <name> --color <color>`, `--monogram <text> --color <color>`, `--emoji <emoji>`, or `--clear-icon`. `t3 project icon <path> <icon flags> --machine <name>` changes only the icon of an existing project and fails with `t3_project_refused` for a directory that is not one. An unknown Lucide name is accepted and shows a blank icon, so pick names from https://lucide.dev/icons.
- Without `--provider` and `--model`, the thread runs the project's default model, which each entry of `t3 projects` carries as `projects[].default_model`. Omit both flags whenever the target project's `default_model` is set and the user named no other model. Pass both only when it is `null` or the user asked for a different model. `--provider` is a provider instance id on that machine, not a driver name: instances are renamed and disabled per machine, and `orchestrator_capabilities` describes only this machine. Take the id from the project's `default_model.instanceId` or from `providers` in `t3 projects`, which lists the instances that machine's running T3 has enabled and is absent when T3 is not running there. A disabled or unknown instance fails with `t3_launch_refused`, and the error lists the enabled ones. Set effort with `--model-option effort=high` for Claude or `--model-option reasoningEffort=high` for Codex.
- Workspace: the project root by default, `--worktree <base> [--branch <name>] [--from-origin]` for a new worktree that T3 sets up, or `--existing-worktree <path>`. That machine checks the base before T3 is asked, after fetching its branch from origin with `--from-origin`, and a base it lacks fails the command with `t3_worktree_base_missing` (exit 3). `--from-origin` fetches branches only, so a commit id or an expression such as `main~2` must already be on that machine. `input.repository` is the project's `host/owner/repo`. When you run the command in a checkout of that same repository (by origin), `input.local.kind` says what it has of the base: `unpushed_branch` means only this machine has the branch, so push it and launch with `--from-origin`; `unpushed_commit` with `input.local.commit` means only this machine has the commit, so push a branch at it and launch from that branch with `--from-origin`; `pushed` means origin has that branch, so add `--from-origin`. `input.local` is `null` in any other checkout. A project that is not a git repository fails a `--worktree` launch with `t3_launch_refused`.
- The thread runs `full-access` unless you pass `--runtime-mode`; nobody on that machine is there to approve its actions. `--plan` starts it in plan mode.
- Put the whole brief in the message; the new agent has none of this conversation. Use `--message-file` for long briefs, up to 100 KiB.
- A launch without `--child` is a hand-off: the user takes over the new thread, and this thread does not manage it. Add `--reply-route` only when the user explicitly asks for the new thread to report back here; never add it on your own. It ends the message with this thread's id and machine and the `homebased message send` command that reaches it, and the reply arrives here as a `HOMEBASED_MESSAGE`.
- `--child` launches a child thread of this T3 thread instead of a hand-off, here (no `--machine`) or on another machine. Launch child threads only this way, never with `t3_thread_launch`, which records no link. See the [child-thread recipe](#child-thread-recipe).
- The JSON result has `thread.thread_id`, `machine_name`, and `thread.link` (`t3code://threads/<environment>/<thread>`), which opens the thread in T3 Code. A `t3-thread://` link would resolve on this machine, so give the user `thread.link`.
- After `t3_launch_outcome_unknown`, repeat the command with the `--request-id` from the error; T3 launches once per request id and returns the same thread.
- `t3_unavailable` means T3 is not running on that machine. `t3_incompatible` means that machine needs `homebased update` or a T3 check; retrying does not help.

### Child-thread recipe

A child thread is a top-level T3 thread that owns one phase, experiment, or long run for the thread that launched it, its parent. It reports to its parent once its work is done, and homebased then settles it. If a later message reopens it for more work, it sends a follow-up report the same way. A child can launch children of its own the same way.

In the parent:

```bash
homebased --json t3 launch [--machine code] --project ~/code/app --child --message-file brief.md
homebased --json thread watch --children --stalled-after 20m
```

- `--child` needs `--message` or `--message-file` and must run in a T3 thread on this machine. It cannot be combined with `--source-thread`. The brief should be complete: the child has none of this conversation.
- The first message ends with the parent's T3 thread and machine, how to sleep on long work with `homebased wait --long`, the `homebased thread report` command for the report and any follow-up, and the `homebased message send` command for a question before then.
- homebased records the link on the parent's machine and the child's. `thread context --children` lists the child with a `child_thread` record, and the parent's `state` is `waiting` until the child has reported or is archived, deleted, or settled ([threads.md](threads.md#child-threads)).
- End the turn. The report arrives as one `HOMEBASED_MESSAGE` that starts `Report from child thread thread_<id>:` ([messages.md](messages.md#child-thread-reports)).
- `--request-id` works as for any launch: after `t3_launch_outcome_unknown`, repeat the command with the same id to get the same thread and link.

In the child, submit long work as tasks and jobs, then sleep on them with `homebased wait --long` ([Sleeping on long work](#sleeping-on-long-work)) and end the turn. Once its work is done:

```bash
homebased --json thread report --summary "<what was done, what was found, and what is left>" [--file report.md]
```

- Run it as the last step of the turn. It is refused with `thread_report_refused` while the child still has open work: a homebased task or job that owes it events, a sleep hold, a T3 subagent due to report to it, or a child thread of its own that has not reported. The error's `input.open` names each one. Wait for that work, then run it again.
- A retry, or a daemon restart, finishes the same report and never sends a second one. After `message_delivery_failed`, run the same command again. Other text in the same turn fails with `thread_report_conflict`; send it with `homebased message send` instead.
- When a later turn reopens the reported child, such as after a user message, and more work follows, run `thread report` again at the end of that turn. It goes to the parent as a follow-up report, and the child settles again after that turn.
- Once the turn ends, the child's machine settles the child in T3, unless a later turn or a user message to the child came first. Do not settle it yourself with `t3_thread_organize`.
