# T3 Code

Read this when the `t3-code` MCP tools are present in your session, or before starting a T3 thread on another machine. Without T3, nothing else here applies.

## Delivery

When a T3 Code thread owns a Claude Code session or a Codex thread, the daemon starts the callback turn through T3 instead of the messaging socket or `codex queue`, so the thread shows it. [messages.md](messages.md) has the exact rules, including retries and unowned sessions.

## Choosing the runner

If the `t3-code` MCP server offers `delegate_task`, prefer it for an `agent` workload that needs no Homebased feature, so T3 shows the child under the thread. Homebased stays the choice for `task` and `container` workloads, Fleet, the resource queue, and `after`.

## Waiting in a Claude thread

By default each event starts a new T3 turn, and the thread shows as idle between events. To have T3 show the thread as Waiting and receive events inside the live session, arm `Monitor` with `homebased task wait` after you submit:

```text
Monitor(
  command: "homebased task wait <id> [<id> ...]",
  description: "<what the tasks do>, e.g. cargo build and CI for the release",
  timeout_ms: 1800000
)
```

Then tell the user the task ids and end the turn.

- Do this only as a root agent. A worker (`HOMEBASED_TASK_ID` is set) never arms a Monitor and keeps using `waiting`.
- Pass 1 to 16 task ids with no duplicates. Each must have been submitted from this session on this machine. Any other id fails with `wait_unavailable` (not your task, a remote origin, or no callback route, which includes queue runs: their `JOB_*` events arrive through normal delivery as [resource-queue.md](resource-queue.md) describes) or `task_not_found`, and prints nothing to stdout.
- The command runs until every task has its final outcome, then exits 0. Each line on stdout is one `HOMEBASED_EVENT {...}` for those tasks and is handled exactly as in [events.md](events.md). Nothing else is printed to stdout.
- A task that is parked on `TASK_WAITING` is followed to its continuation run: the wait switches to the continuation and ends when that run ends. `TASK_REPORTED` and `TASK_CHECK_DUE` keep the wait open. A `TASK_WAITING` with no continuation ends the wait for that task, as do `TASK_SUCCEEDED`, `TASK_FAILED`, `TASK_BLOCKED`, `TASK_CANCELLED`, and `TASK_LOST`.
- While a wait is connected, the daemon gives the task's events to it instead of normal delivery, and counts an event delivered only after the command printed it. An event that was not confirmed within about 5 seconds, for example because the command was killed first, goes through normal delivery, so it can arrive twice. Deduplicate by `(task, seq)` as usual.
- A daemon restart or update does not end the wait: the command reconnects on its own for up to 5 minutes and prints nothing. After that it exits non-zero with `daemon_unavailable`.
- The Monitor times out after `timeout_ms`. When it expires, re-arm it with the ids that are still pending, meaning those whose final event you have not seen. If the Monitor dies or is stopped, events it did not print arrive through normal delivery.
- `--thread <uuid>` overrides the detected thread. You normally do not need it.

## Waiting in a Codex thread

Codex cannot arm a Monitor. To keep the thread in T3's Working shelf instead, submit with `--hold` (or `"hold": true` in the spec). Use it when you will end the turn and wait on the task; without it, nothing changes.

- Once the thread has been idle for a few seconds, homebased adds a placeholder message, "Waiting on homebased: <task names>", that T3 never starts, so the thread shows as Working.
- The task's events end the placeholder and arrive as normal turns. While the task or the waiting chain it parks is still pending, the placeholder returns after each turn.
- A message the user sends ends the placeholder so theirs runs at once. Stop ends it until the next event. A T3 restart cancels it, and homebased adds it again when the thread is idle.
- The flag is accepted and does nothing for Claude threads, which use `task wait`, and for threads T3 does not own.

## Launching a thread on another machine

The `t3-code` MCP tools reach only the T3 on this machine. To start a thread in the T3 on another Fleet machine, use `homebased t3 launch`, which works from any shell, inside T3 or not:

```bash
homebased --json t3 projects --machine code
homebased --json t3 launch --machine code --project ~/code/app \
  --message-file brief.md --worktree main --branch fix/upload
```

- Use it when the user asks for a new thread or independent work on that machine, the way `t3_thread_launch` serves this one. Use a homebased task instead for background work that should report back to this thread as events.
- `--project` is a T3 project on that machine: its id, its workspace root there (absolute or `~/`, which resolves under that machine's home even when your shell expands it), or its exact title. Run `t3 projects` first when unsure; a project missing there fails with `t3_project_not_found` and lists what exists. Add a project in T3 on that machine; homebased does not create them.
- Without `--provider` and `--model`, the thread runs that machine's T3 default (`default_model` in `t3 projects`). When it is `null`, pass both, using the provider instance ids and models from `orchestrator_capabilities`, such as `--provider codex --model gpt-6.1-sol` or `--provider claudeAgent --model claude-opus-5-5`. Set effort with `--model-option effort=high` for Claude or `--model-option reasoningEffort=high` for Codex.
- Workspace: the project root by default, `--worktree <base> [--branch <name>] [--from-origin]` for a new worktree that T3 sets up, or `--existing-worktree <path>`. A bad base branch fails the new thread's run, not the command.
- The thread runs `full-access` unless you pass `--runtime-mode`; nobody on that machine is there to approve its actions. `--plan` starts it in plan mode.
- Put the whole brief in the message; the new agent has none of this conversation. Use `--message-file` for long briefs, up to 100 KiB.
- A launch is a hand-off: the user takes over the new thread, and this thread does not manage it. Add `--reply-route` only when the user explicitly asks for the new thread to report back here; never add it on your own. It ends the message with this thread's id and machine and the `homebased message send` command that reaches it, and the reply arrives here as a `HOMEBASED_MESSAGE`.
- The JSON result has `thread.thread_id`, `machine_name`, and `thread.link` (`t3code://threads/<environment>/<thread>`), which opens the thread in T3 Code. A `t3-thread://` link would resolve on this machine, so give the user `thread.link`.
- After `t3_launch_outcome_unknown`, repeat the command with the `--request-id` from the error; T3 launches once per request id and returns the same thread.
- `t3_unavailable` means T3 is not running on that machine. `t3_incompatible` means that machine needs `homebased update` or a T3 check; retrying does not help.
